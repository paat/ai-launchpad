# R-002 — identity-only sign-in and bounded runtime model use

Tracking: [issue #3](https://github.com/paat/ai-launchpad/issues/3).
Status: accepted need, 27 October 2026. The owner requested protection against model API-credit abuse and explicitly excluded Gmail and Calendar access from Launchpad.

Launchpad uses Google only to establish an identity. It requests no mailbox or calendar permission, stores no provider mailbox credentials, and does not treat a Google account as proof of authority to represent a business. The owner's assistant may connect directly to those services independently.

Catalogue lookup, assessment reporting and progress reporting do not require Launchpad-paid model inference. Any Launchpad-hosted model jobs must have a fixed purpose, bounded inputs and outputs, authenticated access, rate and concurrency limits, and independently enforced owner and global spending limits. A retry or replay cannot obtain another unmetered inference. A timeout does not prove that the provider charged nothing. Service nominations must not automatically trigger unbounded model work.

Until a provider's billable units, conservative reservations and hard limits are implemented and verified, public-runtime live inference must remain unavailable. Tests may use deterministic or subscription-model-authored synthetic fixtures with clear mock labels. No generic proxy to a model API is exposed.

For the current development run the public runtime API budget is exactly $0: tests/CI use deterministic mocks and subscription-based coding-model fixtures with clear mock labels remain valid for development only. Passing mock tests does not establish actual Meta model quality or live integration. Separately, a bounded operator-authorized live quality harness outside the public runtime ([model-quality doc](../model-quality.md)) completed two genuine synthetic setup calls on 2026-10-28 (EN `en-connector-help`, ET `et-connector-help`; usage-based estimate $0.005588 total, not reconciled billing; $2 allocated per attempt and a $10 pilot cap with at most 5 distinct attempts at that time; allocations never refunded). Public runtime activation stays a separate, later decision.

Spending authority (decided 2026-10-29, [issue #20](https://github.com/paat/ai-launchpad/issues/20)): the sole ledger kept its then pinned $10 ceiling, provider, model, prompt version and fail-closed pending rule. The flat $2 per attempt, sized for a full 1M-token context, is replaced by a per-attempt reservation computed from the request actually sent: (UTF-8 bytes of the fixed instructions and input + 2,048 template tokens) as input plus the job's `max_tokens` as output, at the published price, ×2. Byte-level BPE tokens never exceed bytes, so this bounds the request; it is a conservative reservation, not billing. The post-response check compares estimated cost against that attempt's own reservation. The attempt backstop is 1,000; at that time $10 stayed binding. Existing allocations are never refunded. On 1 Nov 2026 ([issue #158](https://github.com/paat/ai-launchpad/issues/158)) the owner raised the all-time ceiling from $10 to $100, matching the owner's Baseten credit. A ledger pinned at exactly $10 is raised once on open; any other existing ceiling still cannot be changed, and the ceiling still cannot be lowered. The 1,000-attempt backstop is unchanged and now binds before $100 for realistic reservations. The friction-loop job `classify_unmet_need` meets this requirement: fixed purpose, de-identified bounded input (no owner, company or session data), strict bounded output (`max_tokens` 512), an authenticated owner-approved flow, per-owner limits (20 needs and 10 classifications per day, 200 needs in total), one attempt in flight globally, server-derived request IDs whose replay never obtains a second inference, and a labelled mock in tests and local mode ([model-quality doc](../model-quality.md#unmet-need-classification-friction-loop-issue-20)).

Acceptance evidence must cover identity isolation, browser-bound sign-in, revocation, repeat requests, concurrency, zero budget, provider failure and truthful user-facing status. Failed cost controls must not disable deterministic catalogue or reporting functionality.
